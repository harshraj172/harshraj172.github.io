Trace-to-Task

From real coding-agent sessions we rebuild the exact situation where the agent slipped, then run the same model again. The mistakes we find are simple and avoidable, and they come back almost every time. That makes them a third kind of failure, sitting between frontier limits and random noise.

The traces did not give us frontier-level failures. They gave us ordinary ones: the agent copies an old setup without checking it fits, fixes the loudest message in a log instead of the real failure, or writes docs from memory instead of the code. These are the "dumb" mistakes users complain about, and they are what this project collects.

What the mistakes look like

Three recurring blind spots

Copies without checking

Sonnet 4.6

Reuses the setup of an old tool for a new one, without checking that the new tool works the same way.

Asked
Follow a plan to swap the app's web terminal for a new terminal tool.
Did
Copied the old terminal's web-address rule for the new tool.
Missed
The new tool expects a different address, so every terminal page shows "404 Not Found". The repo already had the right rule for a similar tool.

Blames the wrong error

Opus 4.7

Fixes the loudest message in a log instead of the real failure, and never asks why it can't see the failure itself.

Asked
"Diagnose and fix this CI error that happens locally," with the end of a failing test log.
Did
Chased warnings printed by tests that actually pass. Its own test run passed, so it stopped.
Missed
Never asked why the user's run fails and its own does not. The tests that really fail stay broken.

Writes docs from memory

Fable 5.1

Describes how a feature works from its impression, not from the code it has just read.

Asked
"Can we add a page in docs showcasing LLM capabilities (with screenshots and short clips)?"
Did
Wrote the whole page in one go, right after looking at the screenshots.
Missed
The page says the AI sees only one summary card. The code, which it had already opened, also sends up to 180 past results.

What they share: each fix is ordinary engineering, but the agent surprisingly misses them.

How a task is made

From a session to a checked task

audit findings → builder fixes · up to 2 rounds
1

Episode

One user request and the agent's work until the next message.

  • The user's next message pushes back on what the agent did.
2

Preflight

A program looks for a real failure signal.

  • Keep it only with clear evidence: the user complained, a test still failed at the end, or the user undid the agent's work.
3

Builder

Finds the root cause and rebuilds the moment.

  • The first wrong decision falls in the first 50% of the agent's steps.
  • The repo is set to the commit from that day.
  • The user's request is copied word for word.
4

Checks

The task must be solvable and not free.

  • Oracle and No-op verification.
5

Audit

Would an ideal expert pass? Is the grading fair?

  • Quality Audit.
↺ findings go back to the builder, up to 2 rounds
6

Trial

The trace's own model runs the task.

  • Run with the same model and Claude Code version.
  • Kept only if it fails the same way.

Why the first wrong decision must come early (within 50% of the steps)

Three things decide whether a failure can be reproduced.

The user's instruction

We have it, word for word.

The environment at that step

We can rebuild it. An agent replays the recorded file edits and fills the gaps, as in Terminal-Universe.

The chat history before it

We cannot keep it. The agent in a task starts from scratch with only the instruction.

So whether a failure comes back depends mostly on the history. We therefore look for episodes where the first wrong decision sits close to the user's request. Then the mistake is not a function of the history, and a fresh agent can make it too. In the tasks kept so far, this decision falls at 0 to 50% of the episode's steps.

What this gives at stage 6, measured on tasks that were built and reached the trial: the model failed again in 90% of them, and made the same mistake as the trace in 52%.

Scale

A large set of instances, not a leaderboard

This is not meant as a standard benchmark with a score to beat. It is a collection of concrete, reproducible instances of simple mistakes, each tied to the model that makes it and labeled with how it fails. The useful size is in the hundreds: 500 to 1,000 tasks, enough to cover many repos, languages, and kinds of slip, and to train or test against them.
